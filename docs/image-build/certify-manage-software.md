# Immutable certify-manage / Certbot application software

Status: source producer implemented; native wheel/build/link and ACME acceptance remain
NO-GO until the Work gates below pass.

This producer implements the certify-manage packaging handoff using the existing
`applications-v1`, `application-software-view-v1` and
`application-software-consumer-v1` contracts. It does not install application
software into Basic, mutate a running issuer volume, contact PyPI at runtime, issue
certificates or provision DNS credentials.

## Compatibility decisions

### Cryptography

certify-manage now accepts `cryptography>=47,<51`. Certbot/acme 5.8.0 require
cryptography >=47 with no lower compatible conflict, pyOpenSSL 26.4.0 supports the
50.x line, and image-build's reviewed cryptography package is 50.0.2.

The selected immutable runtime lock therefore requires:

- certify-manage 0.1.0 from an exact reviewed Git/source artifact;
- Certbot/acme 5.8.0;
- cryptography 50.0.2;
- CFFI 2.1.1 and pycparser 3.0, matching the reviewed image-build source recipes required by cryptography on CPython;
- pyOpenSSL 26.4.0;
- the exact transitive versions encoded by
  `zog.image_build.certify_manage_software.PROFILES`.

No version is resolved at publication time. The lock must provide an HTTPS source
URL, SHA-256 and retained notice path for every distribution. Missing, extra or
changed distributions are rejected. For CFFI 2.1.1 and pycparser 3.0, the producer
also requires the exact reviewed image-build catalogue URL/SHA-256 identities; a
same-version archive from different bytes is rejected.

The Python runtime distributions are application-specific inputs. They do not need
to become Basic/rootfs catalogue packages. Native build-only tooling already
reviewed by image-build (Python setuptools/wheel, maturin, Rust and the
cryptography recipe/toolchain) may be used by the isolated Work build. CFFI and
pycparser are different: cryptography 50.0.2 requires CFFI at runtime on CPython,
and CFFI in turn requires pycparser, so both are explicit immutable runtime inputs
and must appear in the lock and installed distribution set.

### Python and executable paths

The application does **not** ship a second CPython/OpenSSL stack. It binds to the
accepted rootfs CPython 3.15.0rc2 ABI through the artifact compatibility descriptor
and exposes an immutable launcher at:

```text
/applications/certify-manage/bin/python3
```

The launcher executes rootfs `/usr/bin/python3` with `-I -S` and replaces
`sys.path` with only:

1. `/applications/certify-manage/lib/python3.15/site-packages`;
2. the rootfs standard-library / platform-standard-library paths;
3. the corresponding rootfs `lib-dynload` directories required by native standard
   library modules such as `_ssl` and `_sqlite3`.

It therefore does not consume user site-packages, `PYTHONPATH`, mutable issuer
storage or an unrelated host installation.

The canonical Certbot entry point is generated by image-build at:

```text
/applications/certify-manage/bin/certbot
```

with an exact shebang pointing at the immutable launcher. certify-manage's
`CertbotAdapter` accepts only that absolute executable. Selected application
programs likewise invoke the immutable Python path directly.

## Profiles

`http-01` contains the complete core closure and no Cloudflare plugin.

`cloudflare-dns-01` additionally requires:

- certbot-dns-cloudflare 5.8.0;
- cloudflare 5.6.0;
- the exact anyio/httpx/httpcore/h11/pydantic/pydantic-core/annotated-types/
  sniffio/typing-inspection support closure declared in the producer.

The HTTP-only profile rejects installed `certbot_dns_cloudflare` or `cloudflare`
modules. The Cloudflare profile requires both modules and the pydantic-core native
extension.

Both profiles require the cryptography native extension, the CFFI native extension,
pycparser, and the certifi CA bundle. The reviewed source identities are
`cffi-2.1.1.tar.gz` SHA-256
`dd31f52ea1086513bb9df30f8fcee9b8918323ae067a3d5b78bc826a000712be` and
`pycparser-3.0.tar.gz` SHA-256
`600f49d217304a5902ac3c37e1281c9fe94e4d0489de643a9504c5cdfdfc6b29`;
license evidence remains subject to the repository-wide redistribution review.

## Maintained application definitions

A concrete Cloudflare DNS-01 definition is checked in at
`project/applications/certify-manage/cloudflare-dns-01.json`. It binds the full
`cloudflare-dns-01` runtime closure, exact source hashes, notice-copy plan and the
accepted rootfs compatibility descriptor. The definition requires the
`dns-cloudflare` Certbot plugin and keeps credentials/mutable ACME state outside

The definition is intentionally marked `publication_authorized: false` until the
retained pydantic-core Rust per-component grant/notice and selected native-output

DNS-capable immutable runtime has already passed native acceptance.

## Producer flow

A reviewed caller supplies a JSON lock using
`image-build-certify-manage-runtime-lock-v1`. Its compatibility field must bind the
exact accepted rootfs architecture, CPython 3.15.0rc2 SOABI and every required rootfs
SONAME discovered by the native build.

Begin durable installation staging:

```sh
python -m zog.image_build.certify_manage_software \
  --state-dir PROJECT/state \
  begin OPERATION runtime-lock.json
```

Build wheels and install the **exact locked inputs offline** into the returned root.
No network resolver or live `pip install` is part of publication. Build tooling is
outside the eventual artifact; only runtime files belong in staging.

After the exact wheel installation, materialize the deterministic entry points:

```sh
python -m zog.image_build.certify_manage_software \
  --state-dir PROJECT/state \
  materialize-launchers STAGING_ROOT
```

Verify the staging root:

```sh
python -m zog.image_build.certify_manage_software \
  --state-dir PROJECT/state \
  verify STAGING_ROOT runtime-lock.json
```

Finalization independently verifies the lock, installed distribution metadata,
required modules/native extensions, immutable launchers, notice files and absence of
mutable issuer/policy paths. It then publishes one `applications-v1` artifact,
one `application-software-view-v1` view and a verified
`application-software-consumer-v1` binding:

```sh
python -m zog.image_build.certify_manage_software \
  --state-dir PROJECT/state \
  finalize OPERATION runtime-lock.json rootfs-compatibility.json
```

The result freezes the artifact/view IDs, binding digest, exact runtime-lock digest
and canonical Python/Certbot command paths.

## Mutable-state boundary

The immutable runtime image supplies the empty real target:

```text
/var/lib/zog-certify-manage   mode 0700
```

through `image-build-application-data-targets-v1`. box-control overlays the
controller-owned `certificate-data` storage there and refuses a missing,
redirected or wrong-mode target.

The immutable application artifact itself rejects top-level `etc/`, `var/`,
`run/` or other paths outside its software layout and specifically rejects
certificate/key/policy/credential filenames.

`/run` is an image-build/controller runtime facility. Application-image
publication intentionally normalizes it to an empty controller-private root.
Therefore image-build does **not** bake a policy file, token, or persistent
`/run/zog-host` payload into the immutable image. box-control/root-control must
materialize the authorized read-only host capability at:

```text
/run/zog-host/certify-policy/policy.json
```

after the private runtime scaffold is established. Native acceptance must prove the
actual read-only mount, source inode/digest and destination after pivot_root.

## Native Work acceptance

Source publication does not claim these checks. Work must use the exact accepted
rootfs and locked source bytes to:

1. build every wheel from reviewed source without network access and record build
   commands, build backend and produced wheel SHA-256;
2. install only the locked runtime distributions into the durable application
   staging root;
3. run the producer's staging verification and reopen the published artifact/view;
4. execute the immutable Python launcher and import `zog.certify_manage`,
   `certbot`, `acme`, `cryptography`, `cffi`, `pycparser`, `configobj`, `ssl`, and `sqlite3`;
5. run `certbot --version`, `certbot plugins --text`, and offline
   `renew --help` / `certonly --help`;
6. for the Cloudflare profile require `dns-cloudflare`; for HTTP-only require its
   absence;
7. run certify-manage's saved ConfigObj renewal fixture and finite selected
   `inspect` against synthetic protected state;
8. inspect every native extension with readelf, record NEEDED/RPATH/RUNPATH, and
   prove linkage to the selected rootfs ABI/OpenSSL rather than host libraries;
9. verify certifi/public trust, wrong-hostname and unknown-CA rejection;
10. prove no executable/module resolves from `/var/lib/zog-certify-manage`,
    host site-packages, `PYTHONPATH`, or a network-installed wheel;
11. publish artifact/view/consumer identities and verify the same frozen consumer
    binding is admitted by box-control.

Only after those checks may host-deploy Work start isolated selected-program ACME
staging acceptance. No live ACME issuance, Cloudflare credential transfer, nginx
reload or production TLS activation belongs to this producer.
